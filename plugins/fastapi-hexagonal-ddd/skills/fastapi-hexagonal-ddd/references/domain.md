# The domain: tactical DDD

The domain holds the rules, in the words of the business. It performs **no I/O**
and imports **no framework**.

## The toolbox, and the question each brick answers

| Brick | Question it answers |
|---|---|
| **Value object** | Is this thing defined by its value? |
| **Entity** | Does it have an identity that survives its changes? |
| **Aggregate** + root | What must be consistent within the same transaction? |
| **Factory** | How is a valid object born? |
| **Repository** (port) | How is an aggregate found and persisted? |
| **Domain service** | Where does a business rule with no owning object go? |
| **Domain event** | What should be made known when something important happened? |

These are not checkboxes. If the middle-column question does not arise, the
brick is decoration — expensive decoration, because it must be maintained.

**Document the absences.** A project with no domain service and no domain event,
stating why, teaches how to decide. A project exhibiting all seven because the
book lists seven teaches how to tick boxes.

## Ubiquitous language

Names come from domain experts, not from the database. `TaskTitle`,
`EmptyTitle`, `TaskAlreadyCompleted` are business phrases. Catching yourself
writing `TaskRow`, `UserData` or `TaskManagerHelper` means you have slipped to
the technical side.

## Value objects

**The defining property is the absence of its own identity: two value objects
with the same value are interchangeable.** Two `Email("a@b.c")` *are* the same
email; you never ask "which one?".

Immutability and self-validation do not *define* the concept — they are
(excellent) practices that almost always follow.

```python
@dataclass(frozen=True, slots=True)   # frozen → immutable ; slots → no __dict__
class TaskTitle:
    value: str

    def __post_init__(self) -> None:
        cleaned = self.value.strip()
        if not cleaned:
            raise EmptyTitle()
        if len(cleaned) > TITLE_MAX_LENGTH:
            raise TitleTooLong(TITLE_MAX_LENGTH)
        object.__setattr__(self, "value", cleaned)   # normalisation, see below
```

`frozen=True` raises on any assignment, including inside `__post_init__`. To
**normalise** at construction, bypass the guard explicitly via
`object.__setattr__`. It is a deliberate, localised exception: it happens before
the object is visible to anyone, and the object is genuinely immutable
afterwards.

Other idioms are equally valid: `NamedTuple`, `attrs`, a plain class with
read-only properties. Pick one and be consistent.

### The payoff: an always-valid model

Once that barrier is crossed, **not one line of the domain re-checks**. "What if
the title is empty?" stops being a question: an empty `TaskTitle` does not
exist.

```python
Email("bob@example.com")       # ✅ constructed → necessarily valid
user.email = "whatever"        # ❌ impossible: Email refuses construction
```

### A value object performs no I/O

It validates a **form**, never a fact about the outside world. Verifying that an
address *receives* mail is an adapter's job (send a confirmation), not a value
object's. Resolving MX records inside `Email` would make domain validity depend
on DNS: non-deterministic, slow, and able to reject a perfectly good address on
a resolver hiccup — and it would make the domain tests network-dependent, which
is the reliable sign a rule has been mixed with technology.

### Identities are value objects

```python
@classmethod
def generate(cls) -> UserId:
    return cls(uuid.uuid7())          # time-ordered

@classmethod
def from_string(cls, raw: str) -> UserId:
    try:
        return cls(uuid.UUID(raw))
    except ValueError as exc:
        raise InvalidUserId(raw) from exc    # business error, not a raw ValueError
```

Two points, of unequal importance:

- **The identity is generated by the domain**, with no round trip to the
  database. That is the part that matters: whole batches can be built in memory
  before touching storage, and there is no `RETURNING` dance.
- A time-ordered identifier (UUIDv7, ULID) generally improves insert locality in
  a B-tree index compared with `uuid4()`. Not a guarantee, and no substitute for
  indexing against real queries. Also: **a UUIDv7 reveals its creation instant**.
  It is not a security mechanism; if identifier confidentiality matters, decide
  that separately.
- `from_string` translates a stdlib error into a **business** error, which the
  HTTP boundary will turn into a 422. The domain does not leak `ValueError`
  upward.

## Entities

An entity has a **stable identity over time**. A task stays "the same task" when
its title changes. Equality is by identifier, not by value.

```python
def __eq__(self, other: object) -> bool:
    return isinstance(other, Task) and other.id == self.id

def __hash__(self) -> int:
    return hash(self.id)
```

Note `__hash__`: Python sets it to `None` as soon as you define `__eq__`.
Without it the entity cannot go into a `set` or serve as a `dict` key.

### Invariants live in the entity

The entity protects **its own** invariants through its methods. You do not
mutate its state from outside.

```python
task.status = TaskStatus.DONE   # ❌ bypasses the rule, completed_at stays None
task.complete()                 # ✅ rule and coherence guaranteed
```

|  | Anemic model | Rich model |
|---|---|---|
| The object holds | attributes | attributes **and** behaviour |
| The rule lives | in services / routers | in the object |
| A new caller | must rediscover the rule | gets it for free |
| Symptom | setters everywhere | business verbs (`complete`, `rename`) |

**Python nuance.** Leaving attributes public means nothing technically prevents
`task.status = ...`. A stricter model prefixes them `_status` and exposes
read-only `@property`. It is a dial: more protection for more ceremony. What
matters is that the **intended** path goes through the methods and that review
enforces it.

Tooling can help once you move to properties: mypy strict rejects assigning to a
read-only property, and Ruff's `SLF001` rejects the back door `task._status = X`.
Note that **no linter can do anything while the attributes are public** —
without type inference it does not know `task` is a `Task`. Encapsulation is a
design choice, not a linter setting.

## Factories vs. reconstitution

Two different intentions, two entry points:

- `Task.create(...)` — a **factory**: produces a coherent *initial* state
  (status `TODO`, `created_at` now, identity generated).
- `Task.reconstitute(...)` — **rematerialises** something that already exists.
  Imports, replays and persistence mappers all use it. It must not regenerate
  identity or reset `created_at`, and it validates every intrinsic state
  invariant regardless of provenance.

> `create()` plus the transitions answer *"is this state reachable?"*
> `reconstitute()` plus the value objects answer *"is this state valid?"*

For data that already existed elsewhere (an import, a replay), the second
question is the right one — see `reads-and-writes.md`.

## Aggregates

> An **aggregate** is a group of objects treated as a **unit of business
> consistency**. It has a **root**, the only entry point for modifications,
> which guarantees the whole stays valid. Its invariants hold within one
> transaction.

What that definition does **not** say: it does not say "always select every
column, hydrate everything, rewrite everything". The aggregate defines the
**business boundary** and the **modification entry point**; the persistence
strategy is a separate choice that may load partially, write incrementally, or
use optimistic locking. Conflating the two mechanically pushes you toward huge,
expensive aggregates — exactly what you are trying to avoid.

The design question is never "are these objects related?" (almost everything is)
but:

> **Must these objects be consistent within the same transaction?**

### The canonical example

```python
class Order:                                   # ← aggregate ROOT
    def __init__(self, id: OrderId, customer_id: CustomerId) -> None:
        self.id = id
        self.customer_id = customer_id         # another aggregate → by identity
        self._lines: list[OrderLine] = []      # same aggregate → real objects
        self._status = OrderStatus.DRAFT

    def add_line(self, product_id: ProductId, quantity: int, price: Money) -> None:
        if self._status is not OrderStatus.DRAFT:
            raise OrderAlreadySubmitted()
        if self.total() + price * quantity > MAX_ORDER_AMOUNT:
            raise OrderAmountExceeded()
        self._lines.append(OrderLine(product_id, quantity, price))
```

Two decisive observations:

1. **`OrderLine` is *inside* the aggregate, as objects, not IDs.** A line makes
   no sense without its order, and the total must stay coherent with the lines at
   all times. **DDD does not forbid collections of objects.** It forbids
   traversing boundaries *between* aggregates by object navigation.
2. **Everything goes through the root.** `order.add_line(...)` enforces the
   invariant; `order._lines.append(...)` is the back door where all guarantees
   end.

### Choosing a boundary — four questions in order

1. **Is there an invariant crossing these objects?** If changing A must
   immediately constrain B, same aggregate. If they can diverge for a moment
   without the business screaming, they are not.
2. **Do they share a lifecycle?** An order line is born and dies with its order.
3. **What is the plausible maximum size?** An invariant is only checked against
   what you hold. A user containing 50 000 tasks is unmanageable — unbounded size
   is the most reliable signal a boundary is misplaced.
4. **Who needs to lock what?** A big aggregate is contention: two users editing
   two different tasks of the same owner should not block each other.

**When in doubt, prefer small aggregates.** Merging two small ones later is far
easier than splitting a big one.

### One transaction, one aggregate — really?

A frequent DDD recommendation, and a good design heuristic rather than a law. Its
real argument: if you *can* atomically change two aggregates today, maybe the
boundary was not needed — and the habit will not survive the day they live in
two services or two databases.

In practice, in a monolith on a single database, changing two aggregates in one
transaction is common, technically safe, and often the right trade-off. Know
that you are deviating, and why: those are exactly the places to revisit when a
context is extracted (events, eventual consistency, an outbox).

### The giant-aggregate anti-pattern

```python
class User:                     # ❌
    def __init__(self, ...):
        self.tasks: list[Task] = []
        self.notifications: list[Notification] = []
        self.audit_log: list[AuditEntry] = []
```

Every read pulls thousands of rows, every write locks everything, four concepts'
rules mix in one class, and tests become setup monsters. The corrective reflex:
ask which **invariant** would justify that collection. There almost never is one
— it is a **query** disguised as an attribute.

## Relations between aggregates

> Between aggregates: reference **by identity**. Inside an aggregate: objects
> reference each other normally, and form collections where natural.

```python
class Task:
    def __init__(self, *, id: TaskId, owner_id: UserId, ...):
        self.owner_id = owner_id     # ✅ an IDENTITY, not a User object
```

Three reasons, by importance: the **consistency boundary** (the real one),
**decoupling** (the task context needs neither the owner's name nor their email
to apply its rules), and **volume**.

"The children of a parent" becomes an explicit, paginated **query**. When it
serves a screen, put it on an application query port and return a read model:

```python
async def list_by_owner(
    self, owner_id: str, *, limit: int = 100, offset: int = 0
) -> list[TaskSummary]: ...
```

A domain repository may expose a search that returns aggregates only when the
caller will use them to protect invariants. More verbose than an attribute, and
that is the point: the cost and intent of the query are visible where triggered.

### Cardinalities

| Relation | Domain modelling | Infrastructure |
|---|---|---|
| Objects in the **same** aggregate | real object collection via the root | child table, cascade |
| 1→n / n→1 (two aggregates) | the child holds `parent_id: ParentId` | **indexed** FK |
| 1↔1 (two aggregates) | one side only holds the other's ID | `UNIQUE` FK |
| 1↔1 (actually one) | value object composed inside the aggregate | inline columns |
| n↔n (no data on the link) | a collection of IDs on one side | join table |
| n↔n (data on the link) | **reify** the relation as an aggregate | entity table |

**1↔1:** ask first whether it should be *one* aggregate. If B has no independent
lifecycle, B is a value object composed inside A — no relation at all. If it
does and an invariant binds them transactionally, merge them. Otherwise two
aggregates, with **one side only** holding the identity; mutual references
recreate the circular coupling you were avoiding. Default to merging.

**n↔n:** a collection of identities if the sets are small and the link carries
no data. **Reify** as soon as the link carries its own attributes or a rule:
`Student ↔ Course` with an enrolment date and a grade is not an association, it
is an `Enrollment` — a concept the ubiquitous language probably already names.
It has its own identity, its own lifecycle and its own invariant
(`assign_grade` refusing to overwrite), which is exactly why it is an entity and
not a value object.

> **Trigger for reification:** the moment you want to "store something on the
> relation", it is no longer a relation.

Never model n↔n as two mutually pointing object collections (`user.roles` ↔
`role.users`): that is what blows up loading and dissolves aggregate boundaries.

### The join is an infrastructure detail

The foreign key and the SQL join appear only at the ORM level. The domain knows
only a `UserId`. The index on that FK is not decorative — without it,
`list_by_owner` is a sequential scan.

In async SQLAlchemy, implicit I/O from ordinary relationship access is
problematic and commonly raises at runtime. Prefer explicit eager loading with
`selectinload(...)`; SQLAlchemy also offers explicit async mechanisms such as
`AsyncAttrs` when lazy access is genuinely required. Such a `relationship`
lives in the **ORM models**, not in the domain — it is an infrastructure read
tool, not aggregate navigation.
For a joined read view, do not rebuild two aggregates: use a query service
(`reads-and-writes.md`).

## Domain exceptions

Domain errors are **business exceptions**, not HTTP codes. The domain ignores
HTTP; the presentation layer translates.

```python
class DomainError(Exception): ...
class ValidationError(DomainError): ...   # broken value-object invariant
class NotFoundError(DomainError): ...     # missing resource
class ConflictError(DomainError): ...     # uniqueness or state conflict
```

**Do not file everything under `DomainError`.** An unreachable database, an SMTP
timeout, a dead broker are not business errors — they get a parallel hierarchy
(`InfrastructureError`) mapped to 5xx. See `transactions-and-errors.md`.

## Why not a validation library in the domain?

It would be more concise. The argument is one sentence:

> The domain should not depend on a validation/serialisation library whose
> features it does not use.

Pydantic is excellent, and it is the right tool **at the boundary** — HTTP
schemas, configuration. In the core it brings parsing, coercion and JSON
serialisation the domain never uses, at the price of an external dependency in
the most stable part of the project. Stdlib dataclasses give most of the comfort
for zero dependencies.

This is not a law. Some teams accept Pydantic in the domain and accept following
its lifecycle. The non-negotiable part is knowing **why** it is there rather than
finding it there by default.
