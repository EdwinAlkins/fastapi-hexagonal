# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

FastAPI template demonstrating **hexagonal architecture (ports & adapters)**, **tactical DDD**, and Software Craftsmanship. Two bounded contexts — `task` and `user` — with a **`User` 1 → n `Task`** relation used as the worked example of how relations are modeled across the layers.

Docs (README.md, archi.md) and all code/comments are in **French** — match this when adding code.

Stack: FastAPI · SQLAlchemy 2 async · PostgreSQL (asyncpg, behind PgBouncer) · Valkey/Redis cache · Pydantic v2 · pytest · ruff · mypy · uv. Requires Python 3.14 **and a running Docker daemon** — the app needs Postgres and Valkey, and integration tests spin up throwaway ones via testcontainers.

Infra lives one level up: `../docker-compose.yml` (migrate, api, pgbouncer, postgres, valkey, rabbitmq, mailpit) + `../.env.template`. `docker compose up -d postgres pgbouncer` is enough to work on the backend locally (`APP_INIT_DB=true` or `uv run alembic upgrade head` against Postgres).

## Commands

```bash
uv sync                                          # install dependencies
uv run uvicorn task_manager.main:app --reload    # dev server → http://localhost:8000/docs

uv run alembic upgrade head                      # apply migrations (direct Postgres URL)
uv run alembic revision --autogenerate -m "…"    # new revision from ORM models

uv run ruff check .      # lint
uv run ruff format .     # format
uv run mypy              # strict type check (config in pyproject.toml)
uv run pytest            # all tests

uv run pytest tests/unit/domain/test_user.py                  # single file
uv run pytest tests/unit/domain/test_user.py::test_rename_changes_name   # single test
uv run pytest tests/unit                                      # unit only (fast, pure)
uv run pytest tests/integration                               # end-to-end API tests
```

`pytest` uses `asyncio_mode = "auto"` — async test functions need no `@pytest.mark.asyncio`.

## Architecture

The dependency rule is strict: everything points inward, and `domain/` imports no framework. It is **enforced by import-linter** (config in `pyproject.toml`, `[tool.importlinter]`) via two contracts — a `layers` stack `presentation → infrastructure → application → domain` and a `forbidden` contract keeping frameworks out of `domain/`. Run it after changes to the core (fails with the exact offending `module -> module (l.N)`):

```bash
make imports        # or: uv run lint-imports
```

It also runs inside `make lint` and as a pre-commit hook. (A quick manual smoke check is still `grep -rE "fastapi|sqlalchemy|pydantic" src/task_manager/domain/` → must return nothing, but import-linter is the source of truth: it follows the real import graph, transitively.)

Layers under `src/task_manager/`:

- **domain/** — pure Python core. Entities (`Task`, `User`), value objects (validate at construction → an existing object is always valid), business exceptions, and the repository **ports** (abstract). State invariants live here (e.g. `Task.start/complete` raise `TaskAlreadyCompleted`).
- **application/** — one use-case class per action, depending only on domain ports. Inputs/outputs are neutral dataclass DTOs (`application/<ctx>/dto.py`), **not** Pydantic — use cases stay testable without FastAPI.
- **infrastructure/** — driven adapters: SQLAlchemy repository implementations, ORM models, domain↔ORM mappers, config (`pydantic-settings`).
- **presentation/** — driving adapter: HTTP routers, Pydantic request/response schemas, DI wiring, and translation of domain errors → HTTP status codes.

### Vertical slicing

Every layer is sliced **by bounded context**, so a context is a full vertical slice end to end. Genuinely transverse pieces stay at the layer root:

| Layer | Per-context | Transverse (root) |
|-------|-------------|-------------------|
| domain | `domain/{task,user}/` | `domain/shared/` (error bases) |
| application | `application/{task,user}/` | — |
| persistence | `persistence/{task,user}/` (`models`, `mappers`, `repository`) | `database.py`, `converters.py` |
| DI wiring | `dependencies/{task,user}.py` | `dependencies/{session,repositories}.py` |
| schemas | `v1/schemas/{task,user}.py` | — |
| routers | `v1/routers/{task,user}.py` | — |

### Key conventions

- **Identities are UUIDv7, generated by the domain.** `<Ctx>Id.generate()` uses `uuid.uuid7()` (stdlib, 3.14+) — never `uuid4()`: the time-ordered prefix keeps inserts at the right edge of the B-tree instead of fragmenting it, while the identity still comes from the domain (no DB round-trip, no enumerable IDs). A new context's id VO must do the same; unit tests lock the ordering property. (The `uuid4()` in `create_engine` is unrelated — it names prepared statements, nothing indexed.)
- **Reference other aggregates by identity, never by object.** `Task` holds `owner_id: UserId` (imported from `domain/user/value_objects.py`), not a `User`. `User` does *not* carry a `tasks` collection — "a user's tasks" is a query (`TaskRepository.list_by_owner`), not aggregate navigation.
- **Cross-aggregate checks live in the application layer.** `CreateTask`/`ListTasksByOwner` depend on both `TaskRepository` and `UserRepository` and verify the owner exists before acting.
- **Transaction boundary = the HTTP request, not the repository.** `get_session` (in `dependencies/session.py`) commits on success and rolls back on any exception; repositories only mutate the session and never commit. A use case can chain multiple writes atomically. `tests/conftest.py` deliberately reproduces this same commit/rollback boundary.
- **Domain error → HTTP mapping is driven by semantic base classes** in `domain/shared/exceptions.py`: `NotFoundError`→404, `ConflictError`→409, `ValidationError`→422, generic `DomainError`→400. A new context's exceptions just inherit the right base; `presentation/api/error_handlers.py` needs no change (FastAPI walks the MRO). Raise domain exceptions in the core; never `HTTPException` outside presentation.
- **DI is a composition root.** The `presentation/api/dependencies/` package is the only place ports are bound to concrete adapters. Its `__init__.py` is a façade re-exporting everything (routers/app/tests import from `...api.dependencies`); `repositories.py` binds ports→adapters so the per-context modules never import each other. Adding a use case = a `get_*` provider in the context module + an entry in `__init__.__all__`.

### Two SQLAlchemy gotchas (persistence)

- **Cross-file ORM relationships** (`TaskModel.owner` ↔ `UserModel.tasks`) resolve by class *name* via the SQLAlchemy registry, so the target model is a `TYPE_CHECKING`-only import and `init_db` imports both `models` modules to register them. FKs reference the table name string (`"users.id"`), needing no import.
- **Don't shadow the builtin `list`:** a repository `list()` method makes a later `list[T]` annotation in the same class resolve to the method (mypy error). Declare methods returning `list[T]` (e.g. `list_by_owner`) *before* the `list` method.

### Adding a bounded context

Replicate the vertical slice across all layers (`domain/<ctx>/`, `application/<ctx>/`, `persistence/<ctx>/`, `dependencies/<ctx>.py`, `v1/schemas/<ctx>.py`, `v1/routers/<ctx>.py`) and register providers in `dependencies/__init__.py`. The **`user`** context + the 1→n relation is the complete reference example. Note the façade is deliberate for `dependencies/` (a composition root) but *not* for `schemas/` (plain per-context contracts, no centralizing role) — don't cargo-cult it.

## Configuration

Env vars use the `APP_` prefix (or a `.env` file), parsed by `Settings` in `infrastructure/config.py`. `APP_INIT_DB` defaults to `false` (Alembic / Docker). Set `true` locally for a `create_all` at startup without running migrations. `APP_DATABASE_URL` defaults to the PgBouncer exposed by the root compose on port 6432.

### Migrations (Alembic)

Schema changes go through Alembic (`backend/alembic/`). Useful commands from `backend/`:

```bash
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "describe change"
```

Docker Compose runs a one-shot `migrate` service (`alembic upgrade head`) against **Postgres directly** (`postgres:5432`) before `api` / `worker`. The app runtime still goes through PgBouncer — do not point Alembic at the pooler in transaction mode.

### PgBouncer constraints (transaction pooling)

A server connection is only held for the duration of a transaction, which dictates three things — change them together or not at all:

- `?prepared_statement_cache_size=0` in the URL (set by the compose *and* by the `Settings` default) disables SQLAlchemy's prepared statement cache;
- `prepared_statement_name_func` (uuid4-based, in `create_engine`) stops multiplexed clients from colliding on asyncpg's incremental statement names (`DuplicatePreparedStatementError`);
- `pool_pre_ping=True` discards connections the pooler recycled underneath us.

Also unavailable in transaction mode: `LISTEN/NOTIFY`, `WITH HOLD` cursors, session-level `SET`. Bypass PgBouncer (hit `postgres:5432` directly) if you ever need them.
