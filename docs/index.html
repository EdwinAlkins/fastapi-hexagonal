FastAPI Hexagonal

Une référence exécutable, pas un schéma. Un dépôt à lire et à copier pour faire du FastAPI hexagonal comme en vrai, avec les filets de sécurité et le déploiement qui vont avec — pas un CRUD déguisé en slides.

Pourquoi ce dépôt existe#

Dans une application mal structurée, le code métier finit par se dissoudre dans les détails techniques. On ne s'en aperçoit pas en écrivant : on s'en aperçoit en essayant de tester une règle sans lever une base, en changeant d'outil, ou en cherchant six mois plus tard où vit une décision.

Le symptôme n'est pas esthétique. C'est qu'une règle comme « une tâche terminée ne peut pas être terminée deux fois » n'a pas de domicile : elle est réécrite dans un router, oubliée dans un worker, contournée par un script d'import. Ce dépôt donne une adresse à chaque type de décision, et vérifie mécaniquement qu'elles y restent.

La règle est vérifiée, pas affichée#

« Le domaine ne dépend d'aucun framework » est une phrase que tout le monde écrit dans son README. Une règle d'architecture qui n'est pas vérifiée automatiquement se dégrade en quelques mois — alors ici, elle casse le build.

On ajoute un import interdit dans une entité du domaine :

  from __future__ import annotations

  from datetime import UTC, datetime
+ from sqlalchemy import Column

Le build casse, en pre-commit comme en intégration continue :

$ make imports

Analyzed 130 files, 437 dependencies.

Architecture hexagonale (dépendances vers l'intérieur) KEPT
Domaine sans framework BROKEN
…
task_manager.domain is not allowed to import sqlalchemy:

-   task_manager.domain.task.entities -> sqlalchemy (l.10)

import-linter suit le graphe d'imports réel, y compris transitif — là où un grep ne verrait rien. Deux contrats sont déclarés dans pyproject.toml : l'empilement des couches, et l'interdiction faite au domaine d'atteindre fastapi, sqlalchemy, pydantic ou starlette. Tout le reste de ce dépôt — ports, mappers, DTO, composition root — n'est que la machinerie qui rend cette règle tenable.

La forme que ça donne#

Ce qu'on y trouve#

  • Une règle, vérifiée

    Deux contrats import-linter sur le graphe d'imports réel, en pre-commit et en CI. Pas un schéma dans un README.

  • Un domaine qui n'importe rien

    Value objects auto-validés, invariants dans les entités, identités UUIDv7 générées par le domaine. Zéro I/O.

  • Trois adaptateurs entrants

    API HTTP, CLI et worker RabbitMQ appellent les mêmes use cases. C'est la preuve opérationnelle de l'isolation.

  • Erreurs métier ≠ pannes

    Une hiérarchie sémantique mappée en 404/409/422, une autre pour les dépendances indisponibles en 503.

  • Trois niveaux de tests

    Domaine pur, use cases sur ports doublés, intégration sur un PostgreSQL et un Valkey jetables. Pas de SQLite de complaisance.

  • De Compose à Kind

    CloudNativePG, opérateur RabbitMQ, NetworkPolicy testées, HPA, securityContext durci. La même rigueur jusqu'à l'infra.

Jusqu'au cluster#

La plupart des dépôts d'architecture s'arrêtent au docker compose up. Celui-ci va jusqu'à un cluster Kubernetes, parce que c'est là que les décisions prises dans le code se paient — ou se vérifient.

L'exemple le plus net : le pooler tourne en mode transaction, ce qui interdit les prepared statements persistants, le LISTEN/NOTIFY et les SET de session. Cette contrainte d'infra remonte jusque dans le moteur SQLAlchemy de l'application (prepared_statement_cache_size=0, un nom d'énoncé unique par client, pool_pre_ping) — et elle impose que les migrations Alembic, elles, attaquent PostgreSQL en direct via un Job dédié, jamais le pooler. Un dépôt qui s'arrête à Compose ne peut pas montrer ça.

Le métier — un gestionnaire de tâches — est volontairement simple. Il n'est pas le produit : le comment est le produit.

Cette liste de « non » est le point important. Un dépôt qui prétend tout couvrir n'apprend rien à personne, et le chapitre sur les cas où cette architecture est du sur-dimensionnement est écrit avant tous les autres.

Démarrage#

Python 3.14, uv et un démon Docker. La base et le cache tournent en conteneurs ; l'API tourne en local.

git clone https://github.com/EdwinAlkins/fastapi-hexagonal.git
cd fastapi-hexagonal
cp .env.template .env

docker compose up -d postgres pgbouncer valkey

cd backend
uv sync
uv run alembic upgrade head
make run                      # → http://localhost:8000/docs

Pour lancer la stack entière (API, worker, frontend, RabbitMQ, Mailpit, Prometheus) : docker compose up --build depuis la racine.

Et pour vérifier que tout tient — lint, contrats d'architecture, typage strict et les trois niveaux de tests :

cd backend && make check
