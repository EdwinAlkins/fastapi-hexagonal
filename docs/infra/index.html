De Docker Compose à Kubernetes

La plupart des dépôts d'architecture s'arrêtent au docker compose up. Celui-ci va jusqu'à un cluster — parce que c'est là que les décisions prises dans le code se paient, ou se vérifient.

TL;DR — Un cluster Kind à 4 nœuds, PostgreSQL en haute disponibilité par CloudNativePG, RabbitMQ par son opérateur officiel, neuf NetworkPolicy, HPA et PDB. Tout se monte par un script. Et une contrainte d'infra — le pooler en mode transaction — remonte jusque dans le moteur SQLAlchemy de l'application.

Pourquoi aller jusqu'au cluster#

Un docker-compose.yml suffit à faire tourner l'application. Il ne suffit pas à montrer ce qui nous intéresse ici : la continuité entre les décisions de code et les décisions d'exploitation.

L'exemple le plus net traverse toute la pile. Le pooler PgBouncer tourne en mode transaction : une connexion serveur n'est tenue que le temps d'une transaction. Cette décision d'infra interdit les prepared statements persistants, le LISTEN/NOTIFY et les SET de session. Elle a donc trois conséquences directes, à trois endroits différents :

OùConséquence
URL de connexion (api-deployment.yaml)?prepared_statement_cache_size=0
Moteur SQLAlchemy (persistence/database.py)nom d'énoncé unique par client, pool_pre_ping
Migrations (migrate-job.yaml)Alembic attaque PostgreSQL en direct (task-manager-db-rw), jamais le pooler

Trois fichiers, trois couches, une seule cause. Un dépôt qui s'arrête à Compose ne peut pas montrer ça — et c'est précisément le genre de couplage qui se découvre en production quand il n'a pas été rendu explicite.

La topologie#

Ce que Kind ne simule pas Ces « nœuds » sont des conteneurs Docker sur la même machine. Kind reproduit la topologie multi-nœuds — anti-affinité, reschedule, drain, failover — pas la redondance matérielle. Si l'hôte ou Docker tombe, tout tombe ensemble. C'est un banc d'essai pour les comportements Kubernetes, pas une preuve de haute disponibilité.

Correspondance Compose → Kubernetes#

Service ComposeÉquivalent KubernetesCe que ça change
postgresCluster CNPG, 3 instancesFailover automatique, réplication en flux
pgbouncerPooler CNPG, 2 instancesPlus de SPOF sur le pooler
rabbitmqRabbitmqCluster, 3 nœudsCredentials générés par l'opérateur
valkeyStatefulSet, 1 replicaIdentique (le cache est jetable)
migrateJob db-migrateBarrière avant l'API et le worker
apiDeployment ×2 + HPA 2→6Montée en charge automatique
workerDeployment mail-worker ×2Consommateurs concurrents sur la file
frontendDeployment ×2 + HPA 2→4Derrière la Gateway
mailpit, prometheus, redisinsightDeployment ×1Exposés par hostnames *.localhost

Le principe de traduction est simple : ce qui était un conteneur avec un port publié devient un Deployment derrière un Service, et ce qui demandait de la disponibilité passe sous un opérateur plutôt que sous un script maison.

Patch spécifique à Kind — à ne jamais transposer

Le Metrics Server est installé puis patché avec --kubelet-insecure-tls. Sans ce drapeau, il refuse les certificats auto-signés des kubelets de Kind, ne remonte aucune métrique — et le HPA reste bloqué sur <unknown> sans jamais dire pourquoi. C'est le genre de détail qui coûte une soirée quand il n'est écrit nulle part.

Il faut dire aussi ce qu'il fait : il désactive la vérification du certificat des kubelets. Le Metrics Server le documente comme for testing purposes only. Sur un vrai cluster, la voie propre est une CA qui signe les certificats kubelet — ce contournement n'a sa place qu'ici.
